# Data contracts

## Raw capture envelope version 1 (current Kafka input)

The default topic is `raw-market-frames-v1`, not the legacy canonical topic
`raw-trades`. One Kafka record represents one received market-data frame.

| Field | Meaning |
|---|---|
| `schema_version` | Integer `1` |
| `capture_id` | UUID hex assigned once to this captured frame; reused for enqueue retries |
| `source` | Supported venue: `binance` or `mexc` |
| `subscription_symbol` | Configured subscription, not a claim about decoded contents |
| `source_channel` | Subscription URL/channel |
| `feed_type`, `transport` | Currently `trade`, `websocket` |
| `received_at_ms` | Original local frame receipt time |
| `payload_encoding` | `utf8` for text, `base64` for binary |
| `payload` | Uninterpreted original text or losslessly encoded bytes |

Socket control messages are not market frames: MEXC subscription acknowledgments
are validated during connection setup and known successful PONG/repeated-ack
responses are excluded. Unexpected text is captured and diagnosed downstream.
Malformed market JSON/Protobuf is still captured. This is not an archive of TCP
or WebSocket protocol frames, nor recovery of data never received/published.

The source boundary exposes `frame_json`, `source_kind`, `source_location`,
optional `source_key`, nullable Kafka topic/partition/offset, and timestamp.
Only Kafka is a production reader today; fixture DataFrames verify the boundary.
Normalization checks envelope/source-key consistency and decoded symbols against
the subscription. A failed MEXC decode rejects the whole frame, not a silent
partial selection of valid deals.

## Kafka key

```text
<source>:<symbol>
```

The key defines the ordering boundary. Examples are `binance:BTCUSDT` and
`mexc:BTCUSDT`.

## Canonical trade version 2

This remains the shared business representation inside processing. New ingestion
does not publish it to Kafka. It is still the legacy `raw-trades` wire contract.

| Field | Purpose |
|---|---|
| `schema_version` | Contract compatibility; fixed to `2` |
| `event_id` | Stable deduplication identity |
| `source` | `binance` or `mexc` |
| `event_time_ms` | Exchange message time |
| `trade_time_ms` | Economic trade time used for windows |
| `received_at_ms` | Local ingestion time |
| `symbol` | Uppercase shared market symbol |
| `source_event_id` | Native exchange trade ID when available |
| `price`, `quantity` | Positive decimal strings |
| `trade_side` | Source-reported or derived buy/sell classification |
| `is_buyer_maker` | Binance flag; null when unavailable |
| `source_payload_encoding` | `utf8-json` or `base64-protobuf` |
| `source_payload` | Exact retained source message |

Binance event IDs use `binance:<symbol>:<trade-id>`.

Current MEXC aggregate deals expose `tradeId`, so their preferred identity is
`mexc:<symbol>:<trade-id>`. If an older or empty-ID frame is received, the adapter
uses `mexc:<sha256-of-frame>:<deal-index>`. That fallback deduplicates identical
frame replay but cannot prove economic uniqueness across differently encoded
frames.

Prices/quantities use plain decimal strings (for example `"0.00000001"`, not
`"1E-8"`) in the internal canonical JSON generated by Spark-worker decoders and
in the legacy topic. JSON serialization preserves exact decimal values without
converting through floating point. Shared Spark validation casts
them to explicit decimals. A raw Kafka value contains provider data, not these
already-normalized business fields.

## Provenance, diagnostics, and replay

One raw Kafka record can expand into many canonical events. `frame_event_index`
records the zero-based position, while `event_id` remains the business identity.
The raw serving table uniquely identifies source rows by
`(source_kind, source_location, frame_event_index)` and trades by `event_id`.
It preserves capture ID and original Kafka location as well.

The raw serving sink rejects conflicting values for the same event ID within a
batch or against retained `live_trades` and `latest_trades` rows. The compared
fields are source, symbol, trade time, price, quantity and side; receipt time
and capture metadata may differ on an exact duplicate. Reusing a retained source
location/index for another event ID also fails. These errors roll back serving
rows, diagnostics, counters and the batch marker together; they do not create
a quarantine row. Fix the conflict before retrying. Once both serving tables
have forgotten an ID, they cannot establish its previous contents.

Kafka enqueue backpressure retries the same serialized envelope asynchronously
for up to `KAFKA_ENQUEUE_TIMEOUT_SECONDS` (default 10). An exhausted timeout,
shutdown or cancellation while unqueued is reported as failure, not a source
reconnect. This is bounded in-memory retry, not a durable outbox or offline
backfill guarantee. Pending broker deliveries are flushed and failures reported
at shutdown.

`raw_market.rejected_frames` retains original envelope text, error reason, source
location/index, and batch context. A failed frame produces one diagnostic row;
shared row validation may also quarantine a normalized sub-event. Retries cannot
create another diagnostic at the same location/index. This is PostgreSQL
quarantine, not a new Kafka DLQ publish. Diagnostics and trade serving changes
commit with batch evidence in one transaction and have bounded retention.

The raw query binds its checkpoint UUID to a database query-history row. Normal
same-history batch retries are skipped; a new checkpoint against old output is
rejected. Retained raw input permits reprocessing only through a deliberately
isolated database/checkpoint procedure. There is no permanent archive or S3 reader.

## Candle replacement snapshots (opt-in query)

`common/contracts/candle.py` validates the output of the isolated candle
prototype. Its business key is `(source, symbol, interval, window_start_ms)`;
the exclusive end must match the aligned interval. The sink and custom stateful
processor support `1m` and `5m`. `prototype_candles(..., interval="5m")` builds
five-minute state directly from trades, not by summing one-minute snapshots.
Each interval uses a separate query/checkpoint. The runner accepts
`--interval 1m|5m` (default `1m`); `make candles CANDLE_INTERVAL=5m` selects the
five-minute query. Dashboard interval selection reads existing snapshots, not
an aggregation of stored one-minute versions.

OHLC uses decimal(28,10); base-asset volume uses decimal(38,10). Count and
revision are positive integers. Each snapshot replaces the previous totals,
never adds to them. Revision is ordered only within the same registered
checkpoint history. Identical revisions are no-ops, conflicting same-revision
content fails, and stale revisions are ignored. Higher revisions may not
regress cumulative count/volume/high/low. A final snapshot cannot reopen or
be revised in the same history. Finalization does not prove complete capture.

Migration `005_create_candle_serving.sql` adds separate candle, history and
batch-marker tables. The writer locks interval ownership and commits snapshot
changes and their batch marker atomically. A retry after a successful commit
is skipped; checkpoint-only resets are rejected. This is a PostgreSQL write
protocol, not a Kafka/ClickHouse exactly-once claim. The new migration/writer
are connected through `processing.spark.candle_pipeline`, a separate opt-in
raw-Kafka query. The default trade runner is unchanged; Streamlit now reads
these stored snapshots in its separate candle section. The read is bounded to
200 recent candles per selected exchange/symbol/interval, ordered chronologically.
Charts use floats only for rendering; the inspection table preserves exact
decimal strings and explicit UTC boundaries. Missing windows are not filled.
Use `make db-migrate` before `make candles` or `make candles-once`; the latter
does not force recent windows to finalize. The candle checkpoint is
`checkpoints/candles-1m-postgres-v1` or `checkpoints/candles-5m-postgres-v1`,
separate from each other and the trade checkpoints. Do not reuse one interval's
state for another. Both intervals currently use the same configured watermark
delay, independent of their window duration; five-minute state can retain more
IDs and needs its own capacity measurements.

## Read-time larger candle rollups

Migration `006_create_candle_rollups.sql` adds the stable, read-only function
`raw_market.candle_rollups(source, symbol, interval, limit)`. It supports `15m`,
`1h`, `1d` and `1w`, exclusively from current `5m` rows. One-minute rows and
batch/revision history are not summed. Updating a base snapshot changes the
next query result; no new Spark query, checkpoint or materialized refresh is needed.

Open comes from the earliest base candle; close from the latest. High/low use
max/min; volume and trade count are summed with exact numeric arithmetic.
Windows are fixed UTC intervals, with days beginning at midnight and weeks at
Monday midnight. End boundaries are exclusive. Limit selects the latest parent
windows, returned chronologically. Reads are capped at `limit * expected_slots`
latest base rows; this includes every base row of the selected parent windows.

Expected base slots are 3, 12, 288 and 2,016 respectively. `base_windows` counts
observed slots; `expected_windows` is the full parent width. No missing slots,
zero-volume bars or empty parent windows are invented. Gaps can mean future
slots, quiet markets or capture gaps; this model cannot distinguish them.

`all_observed_final` records whether every observed child is final. A rollup's
`is_final` additionally requires all expected slots. The UI shows Developing
when any observed child is developing, Partial when all observed children are
final but coverage is incomplete, and Final only when both conditions hold.
Even Final/full coverage is not proof of complete exchange capture: a base
candle may have begun mid-window or missed trades.

Computed rollups have no checkpoint revision; the dashboard uses `revision=None`
and displays Computed. `updated_at` is the latest base update, not query time.
Base-window counts and conservative finality are exposed for Grafana as well
as Streamlit. Base history retention determines how far rollups can be queried;
the function cannot reconstruct deleted or uncaptured data. Large weekly reads
still require performance measurements; they are not a precomputed OLAP store.
